# Prototype: sherlodoc client-side search for stdlib + compiler-libs

A working proof-of-concept of indexing the OCaml **standard library and
compiler-libs** with [sherlodoc](https://github.com/ocaml/odoc/tree/main/sherlodoc)
and exposing the result as **serverless, client-side search** inside
odoc-generated HTML (the `js` database format).

This explores sherlodoc as a modern alternative to the hand-rolled
`search.js` / `index.js` that ships in the compiler manuals today (see
`../../SERVING.md` §6–§7). Compared to the current ocamldoc-scraped index it adds
**type-based search** and covers **compiler-libs** — but it requires the API docs
to be generated by **odoc**, not the legacy **ocamldoc** that produces today's
`libref/` / `api/` HTML.

## Contents

- `reproduce.sh` — end-to-end: isolated opam switch → `odig odoc` → `sherlodoc
  index` (js + marshal) → `odoc html-generate` wired to the search assets → CLI
  smoke test. Regenerates everything; commits no build artifacts.
- `cdp_search_test.py` — drives the **real generated page** in headless Chrome via
  the DevTools Protocol: navigate → focus the search bar → type → read the
  worker-rendered `.search-result` DOM. The end-to-end browser proof.
- `cdp_debug.py` — builds the search Web Worker in-page and captures its
  `onmessage` / `onerror` (used to isolate the load-order bug below).
- `cdp_order.py` — compares the two `importScripts` orders head-to-head.
- `ocaml-cdp-test/` — an OCaml port of `cdp_search_test.py` built on the
  [`cdp`](https://ocaml.org/p/cdp) library, extended into a **parity check**
  against `5.3/api` (see below).
- `reproduce_v2.sh` — the same pipeline as a **single `odoc_driver` command**,
  plus `--json-output` and an ocaml.org format check (see the v2 section below).
- `doccheck/` — a verbatim copy of ocaml.org's `.html.json` parser
  (`doc_from_string` from `src/ocamlorg_package/lib/documentation.ml`) as a
  standalone executable; used by `reproduce_v2.sh` to prove format
  compatibility.

## Quick start

```bash
./reproduce.sh
python3 -m http.server 8777 --bind 127.0.0.1 --directory ./_html
# open http://127.0.0.1:8777/ocaml/Stdlib/index.html, press '/', search
```

## The pipeline

1. `odig odoc` builds odoc docs for the switch. The stdlib is the `ocaml`
   package; compiler-libs land under `ocaml/compiler-libs/`. A single
   `find .../odoc/ocaml -name '*.odocl'` sweep catches both.
2. `sherlodoc index` consumes `.odocl` (or `.odoc-index`) files and writes a DB.
   `--favoured-prefixes` already defaults to `Stdlib.`. Stdlib submodules
   (`List`, `Map`, …) live *inside* `stdlib.odocl` as children of `Stdlib`, so
   filtering out the `__`-prefixed internal aliases loses nothing.
3. `js` DB (`db.js`) + the jsoo engine (`sherlodoc js` → `sherlodoc.js`) give
   serverless, in-browser search; `marshal` suits CLI/server.
4. `odoc html-generate --search-uri …` wires both JS files into every page's
   search bar. `odoc_search.js` lazily spawns a Web Worker that
   `importScripts()` them and answers queries via `postMessage`.

Verified (OCaml 5.3.0, odoc/sherlodoc 3.2.1): 352 odoc units indexed; name,
docstring, and type/polarity search all return correct hits for both libraries,
confirmed in a real browser — e.g. `List.map`, `: ('a -> 'b) -> 'a list -> 'b
list`, `Cmt_format.read`, `: Env.t`.

## OCaml parity test (`ocaml-cdp-test/`)

An OCaml rewrite of `cdp_search_test.py` that doubles as a **coverage check
against the shipping `5.3/api`**. It drives the same headless-Chrome page but, for
**every top-level module documented in `5.3/api`** (stdlib + compiler-libs), types
`Module.` into the search bar and asserts the module appears as a dotted-path
segment in the worker-rendered results.

- Uses the [`cdp`](https://ocaml.org/p/cdp) library for JSON-RPC framing and
  response/event demux (`Cdp_envelope.request` / `parse`). `cdp` is
  transport-agnostic, so the transport is brought in separately:
  `cohttp-lwt-unix` for `/json` target discovery and `websocket-lwt-unix` for the
  socket. (`Cdp_json.t = Yojson.Basic.t`, so results use plain Yojson access.)
- `parity_modules.txt` is the parity target, generated from `5.3/api`: 122 real
  modules, plus 3 ocamldoc-only pseudo-pages (`Format_tutorial`,
  `Ocaml_operators`, `Compiler_libs`) marked `pseudo` and expected to be absent.
- Query strategy: `Module.` (trailing dot) scopes the search to that module —
  necessary because a bare short name fuzzy-matches neighbours first (e.g. `Str`
  surfaces `String`/`Stream` before the real `Str`).

```bash
# in the proto switch (needs: cdp websocket-lwt-unix cohttp-lwt-unix)
cd ocaml-cdp-test
opam exec --switch=../_switch -- dune build
./_build/default/parity_test.exe http://127.0.0.1:8777/ocaml/Stdlib/index.html parity_modules.txt 9222
```

**Result: `PARITY: 122/122 real modules found`**, with the 3 pseudo-pages
correctly absent. The odoc/sherlodoc index has full module-level parity with the
legacy `5.3/api` — the only gaps are ocamldoc tutorial/aggregation pages that
aren't real OCaml modules.

## v2: one `odoc_driver` command + the ocaml.org format (`reproduce_v2.sh`)

The hand-rolled pipeline above predates the discovery that odoc ships its own
drivers (`src/driver/` in [ocaml/odoc](https://github.com/ocaml/odoc) —
`odoc_driver_voodoo` is what ocaml-docs-ci runs). The released
[`odoc-driver`](https://ocaml.org/p/odoc-driver) 3.2.1 collapses steps 1–5 of
the pipeline into:

```bash
odoc_driver ocaml --json-output --html-dir _html_v2
```

Verified results (OCaml 5.3.0, odoc/odoc-driver/sherlodoc 3.2.1):

- **970 pages, each emitted twice**: native odoc HTML *and* an `.html.json`
  fragment file (`--json-output` = odoc's `html-generate --as-json` mode), plus
  per-package `sidebar.json` and `status.json` — the exact format
  ocaml-docs-ci/dill emits and ocaml.org consumes for `/p/` package docs.
- **All 970 `.html.json` files parse with ocaml.org's own reader**: `doccheck/`
  holds a verbatim copy of `doc_from_string` (a strict, field-for-field pattern
  match) — 970 pass, 0 fail. Spot checks: `Stdlib.List` yields 5 breadcrumbs, a
  10-entry toc, 65 kB of content.
- Content lands under `ocaml-compiler/<library>/…`, e.g.
  `ocaml-compiler/stdlib/Stdlib/List/` and
  `ocaml-compiler/compiler-libs.common/Typedtree/`. Passing the virtual
  package `ocaml` selects its dependency closure.
- The driver wires the search assets **in the correct order by itself**
  (finding 1 below is handled), and builds the per-package sherlodoc DBs:
  `ocaml-compiler/sherlodoc_db.js` ≈ 6 MB for stdlib + compiler-libs, matching
  v1. Whole tree ≈ 80 MB.

This is the basis of the proposal to side-load CI-built compiler docs into
ocaml.org: consumer-side RFC
[ocaml/ocaml.org#3909](https://github.com/ocaml/ocaml.org/issues/3909),
CI companion issue [#14](https://github.com/ocaml-web/html-compiler-manuals/issues/14).

## Findings worth keeping (things the CLI path does NOT catch)

1. **`--search-uri` order is reversed from the upstream README.** The worker
   `importScripts(search_urls…)` in flag order, and `sherlodoc.js` calls
   `sherlodoc_db()` **at load**, so the DB must be defined first:

   ```
   odoc html-generate --search-uri db.js --search-uri sherlodoc.js …   # correct
   odoc html-generate --search-uri sherlodoc.js --search-uri db.js …   # README order: FAILS on 3.2.1
   ```
   The wrong order throws `Uncaught TypeError: c.sherlodoc_db is not a function`
   inside the worker — invisible to `sherlodoc search`/`serve`, which never use
   `importScripts`.

2. **The Web Worker is created lazily on the search bar's `focus` event**, then
   fed by `input`. Automation/tests must fire `focus` before typing or `worker`
   is undefined.

3. **Released `sherlodoc 3.2.1` ≠ the in-tree dev source.** The vendored source
   supports repeating `--db`/`-o` to emit several formats in one pass; 3.2.1 does
   not (`--db cannot be repeated`) — so js and marshal need separate index passes.

4. Environment gotchas for the headless-browser check: Chrome's new DevTools
   needs `--remote-allow-origins='*'` for a CDP websocket, and you must disable
   the HTTP cache (or cache-bust the URL) between regenerations or the browser
   serves a stale page.

5. **Pin the switch via `OPAMSWITCH`, not `opam exec --switch` alone** when
   running `odoc_driver`. `opam exec --switch=` puts the switch's binaries on
   PATH but does **not** override an inherited
   `OPAMSWITCH`/`OPAM_SWITCH_PREFIX` (e.g. set by direnv in another project).
   `odoc_driver` makes its *own* opam queries, which then resolve the wrong
   switch — odoc reads another compiler's `.cmt` files and dies in
   `Cmt_format.read` (magic mismatch) under `odoc classify`, as an opaque
   `Worker_pool.Worker_failure`.
